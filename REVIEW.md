# REVIEW.md

Defects found in the starter `app/main.py`, each with the location, root cause, a
concrete input that would expose it, and how the fix works.

---

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `list_employees` L93 — `skip = page * page_size` | **Off-by-one in pagination.** Page 1 skips `1 × 20 = 20` rows, returning page 2's data; page 1 always comes back empty. | `GET /employees?page=1` with any seeded data returns `{"items": []}` even when the collection has rows. | Changed to `skip = (page - 1) * page_size`. |
| 2 | `list_employees` L94 — `count_documents({})` | **total ignores the department filter.** The spec says "total counts the filtered set, not the whole collection." | `GET /employees?department=Engineering` with 2 Engineering and 4 other employees returns `total=6` instead of `total=2`. | Changed to `count_documents(q)` where `q` carries the department filter. |
| 3 | `list_employees` L95 — no `.sort()` | **Results are unordered.** The spec mandates "sorted by `emp_code` ascending." | Any multi-employee response comes back in insertion order (random from grader's perspective). | Added `.sort("emp_code", ASCENDING)` before `.skip().limit()`. |
| 4 | `punch_in` L101–102 — no None-check on `emp` | **Missing 404 on unknown employee.** `db.employees.find_one()` returns `None` for an unknown `emp_code`; the next line `emp["shift_start"]` raises `KeyError` → FastAPI converts that to a 500. | `POST /attendance/punch-in` with a non-existent `emp_code` → `500 Internal Server Error` instead of `404`. | Added `if not emp: raise HTTPException(404, "employee not found")` immediately after the lookup. |
| 5 | `punch_in` L102 — `datetime.fromtimestamp(ms / 1000)` | **Server local-time zone used, not IST.** On a UTC server `datetime.fromtimestamp` returns UTC, so extracting the date gives the UTC date, which is 5 h 30 min behind IST. For a punch-in at 01:00–05:29 IST the recorded `date` is one day earlier than it should be. | Employee with shift 09:30–18:30 punches in at 01:45 IST (epoch ms representing 2026-07-07T20:15:00Z). Starter records `date = "2026-07-07"` (UTC date); correct IST date is `2026-07-08`. | Replaced with `datetime.fromtimestamp(ms / 1000.0, tz=UTC)` (UTC-aware), then use the IST-aware `_attendance_date()` helper to derive the correct calendar date. |
| 6 | `punch_in` L102 — `datetime.now()` (no tz) | **Naive fallback timestamp.** When `punched_at` is omitted the starter calls `datetime.now()` which returns a naive (no timezone) datetime. Storing naive datetimes and later comparing them with `tz_aware=True` PyMongo results crashes or silently gives wrong ordering. | Any punch-in without `punched_at` on a UTC server stores a naive datetime that becomes timezone-incorrect when read back. | Replaced with `datetime.now(tz=UTC)` and applied `_trunc()` to remove sub-second precision (R1). |
| 7 | `PunchInIn` model — `punched_at: Optional[int] = None` | **No range validation on epoch milliseconds.** The spec says values below `100_000_000_000` (seconds-looking) must be rejected with 422. A client sending `1751000000` (seconds, looks like a valid future date) is silently accepted and stored. | `POST /attendance/punch-in {"emp_code": "EMP0001", "punched_at": 1751000000}` → 201, with a punch_in timestamp in year 1970. | Added `Field(None, ge=100_000_000_000, le=4_102_444_800_000)` to `punched_at` in `PunchInIn` (and identically in `PunchOutIn` and `RegularizeIn`). |
| 8 | `punch_in` L104–105 — `find_one(…)` then `insert_one(…)` | **TOCTOU race condition.** Two identical requests arrive simultaneously: both pass the `find_one` check (neither sees the other's document yet), both call `insert_one`, and both succeed → two punch-in documents for the same `(emp_code, date)` → data corruption. The spec explicitly says "do not rely on check-then-insert." | Run two concurrent `POST /attendance/punch-in` requests for the same employee on the same day using `asyncio`/threads. Both return 201. | Removed the `find_one` pre-check entirely. The unique compound index on `(emp_code, date)` guarantees exactly one insert succeeds at the database level; `DuplicateKeyError` is caught and converted to 409. |
| 9 | `compute_late_minutes` L36–37 — `int(diff / 60) > 10` | **Off-by-one at the grace boundary.** The condition converts to whole minutes first (`int(601/60) = 10`) then checks `> 10`, which is `False`, so a punch-in at 09:40:01 (601 s late) incorrectly returns `late_minutes = 0`. The spec example says 09:40:01 → `late_minutes = 10`. | Employee with shift 09:30 punches in at 09:40:01 IST. Starter returns `late_minutes=0`; expected is `10`. | Changed the guard to compare raw seconds: `if diff_s > 600: return int(diff_s / 60)`. This correctly returns `10` for 601 s and `0` for 600 s. |
| 10 | `compute_late_minutes` L35 — `punch_in.replace(hour=h, minute=m, …)` | **IST ignored; shift_start built on a naive datetime.** `replace()` on a naive datetime creates a naive shift_start, so the comparison is server-time not IST. For a UTC server, shift 09:30 IST is 04:00 UTC; the diff is computed in UTC, so a punch-in at 04:05 UTC (09:35 IST, inside grace) shows as 5 min late in UTC but should be 0. | Employee on shift 09:30 punches in at 09:35 IST on a UTC server; starter reports `late_minutes=5` instead of 0. | Replaced the entire function. The shift-start datetime is built as an explicit IST-aware datetime on the attendance date: `datetime(d.year, d.month, d.day, h, m, 0, tzinfo=IST)`. |
| 11 | `compute_overtime` L46–47 — naive `punch_out` vs. aware `end` | **TypeError at runtime.** The starter builds `end` with `tzinfo=IST` (aware) but `punch_out` from MongoDB is naive when `tz_aware=False` (the default `MongoClient`). Comparing aware and naive datetimes raises `TypeError: can't compare offset-naive and offset-aware datetimes`. | `POST /attendance/punch-out` with any valid payload crashes the server with a 500. The bug is invisible in the starter because punch-out was never implemented, but it would have crashed immediately. | Switched the `MongoClient` to `tz_aware=True`, so all BSON dates come back as UTC-aware. `compute_overtime` builds `shift_end_ist` as an IST-aware datetime using the correct day (att_date+1 for overnight shifts). |
| 12 | `compute_work_hours` L41 — `round(…, 2)` | **Banker's rounding, not half-up.** Python's built-in `round()` uses IEEE 754 banker's rounding (round half to even). R4 explicitly requires half-up. Example: `round(9.125, 2) = 9.12` (banker's), but half-up gives `9.13`. | `work_hours` for a 9.125-hour shift stored as `9.12` instead of `9.13`; analytics that rely on stored `work_hours` values are wrong. | Replaced with `_half_up()` which uses `Decimal.quantize(…, rounding=ROUND_HALF_UP)` throughout. |
| 13 | `list_attendance` L144 — `list(db.attendance_logs.find(q))` | **Loads the entire filtered collection into Python memory.** On a 100 k-record dataset this exhausts memory and times out. The spec explicitly says "do not load the collection into memory." | `GET /attendance` on the grader's ~100 k dataset causes OOM / timeout. | Moved sort, skip and limit to the MongoDB cursor: `.sort(…).skip(skip).limit(page_size)`. `count_documents(q)` gives the total without fetching documents. |
| 14 | `list_attendance` L93–95 (implicit) | **In-Python pagination on top of in-memory load.** `docs[(page - 1) * page_size : page * page_size]` is only correct after loading all results, which is itself wrong (bug #13). | Same symptom as bug #13 plus wrong results when page > 1 after the in-memory sort. | Removed entirely; server-side `.skip().limit()` is the fix. |
| 15 | `create_employee` L82 — `datetime.now()` (no tz) | **Naive `created_at` stored in MongoDB.** When `tz_aware=True` PyMongo reads it back as UTC-aware but the stored document has no timezone marker, causing inconsistency. Response also serialises it as an ISO string, not epoch ms. | `POST /employees` returns `"created_at": "2026-10-13T05:00:00"` (string, UTC) instead of `1728799200000` (epoch ms). | Changed to `datetime.now(tz=UTC)`. The `_ser_employee()` helper converts it to epoch ms via `_to_ms()`. |
| 16 | `punch_in` response — `doc["punch_in"]` is a raw `datetime` | **Instants serialised as ISO strings, not epoch ms.** FastAPI's JSON encoder renders `datetime` objects as ISO 8601 strings. The spec mandates all instants as integer epoch milliseconds. | `POST /attendance/punch-in` response: `"punch_in": "2026-07-06T04:00:00"` instead of `1751774400000`. | All document serialisation goes through `_ser_record()` / `_ser_employee()`, which call `_to_ms()` on every datetime field, including inside `history[].changes`. |
| 17 | `health` L73–74 — unconditional `{"status": "ok"}` | **Health check never returns 503.** The spec says "Returns 200 only if MongoDB answers a ping, otherwise 503. The runner polls this before testing." A server with a broken MongoDB connection looks healthy. | Take MongoDB offline; `GET /health` still returns 200, so the test runner proceeds and every subsequent test fails with confusing errors. | Wrapped in `try/except`: call `db.command("ping")`; on any exception raise `HTTPException(503)`. |

## Items examined and decided NOT to be defects

| Item | Reasoning |
|---|---|
| `emp_code` uniqueness enforced only in application code | The starter creates an index only on `_id` (MongoDB default). However, this is listed as a *missing feature* (indexes are the candidate's job per README), not a starter defect per se. Fixed anyway by creating a `unique=True` index on `emp_code` at startup. |
| `PunchInIn.status` default `"PRESENT"` | Correct per the spec. |
| `compute_work_hours` formula `(punch_out - punch_in).total_seconds() / 3600` | The arithmetic is correct; only the rounding function was wrong (bug #12). |
| `load_dotenv()` at module level | Correct pattern; real environment variables win over `.env` as the spec requires. |
